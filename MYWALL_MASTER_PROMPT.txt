6. REQUIRED BEHAVIOR CONTRACT

B01 — Anonymous access
The root page opens directly to the wall. Reading and posting require no signup, login, email, or mandatory name form.

B02 — Composition and validation
Visitors can type or paste a multiline message. Enforce a maximum of 280 characters and show an accurate counter. Reject empty and whitespace-only submissions. Define character counting consistently in the UI and database, including emoji and pasted Unicode text. Unicode code-point counting is a reasonable explicit choice because it can align with PostgreSQL char_length; do not accidentally mix it with JavaScript UTF-16 length or an inconsistent native maxlength rule. Handle input composition without corrupting text. Keep validation helpful and near the input.

B03 — Share and confirmed save
Share is disabled for invalid input and while that submission is pending. Prevent rapid double activation from creating two rows. Show useful pending feedback. Save a real row in Supabase. Clear only the successfully submitted draft after confirmation; protect newer text typed during the request, or lock the composer while saving. Preserve the draft on failure. Do not report success solely because a client-side array changed.

B04 — Reading and ordering
Fetch real posts, initially the newest 50, ordered by authoritative creation time with a deterministic tie-breaker. Render author, content, and timestamp separately. Provide Load older or an equally simple paged path when more than 50 exist. Use stable ordering/cursors so arriving messages do not produce skipped or repeated older entries.

B05 — Persistence
The submitted row remains after reload and can be read in a fresh browser context with empty local storage. Supabase is the source of truth. Never silently switch production to browser storage, invented records, or a mock API.

B06 — Realtime
Use Supabase Realtime Postgres Changes for INSERT events on the posts table. Another independent browser context must receive a newly created post without reloading. Reconcile events and insert responses by primary key so a sender sees one row. Prevent a slower initial fetch from overwriting newer events. Subscribe and fetch using a deliberate strategy that closes the initial loading gap. On reconnect, reconcile with the database to recover missed entries. Remove channels and listeners on cleanup; React development behavior must not accumulate subscriptions.

B07 — Loading, empty, failure, and recovery
Distinguish initial loading, an empty wall, a failed fetch, an in-progress save, a rejected save, and a confirmed save. A fetch error is not an empty feed. Let visitors retry recoverable failures without losing a draft. If Realtime is unavailable, retain functioning reads/writes and provide an honest recovery path; do not show a false connected state. Keep setup details out of ordinary product copy and place developer guidance in documentation or development diagnostics.

B08 — Safe text rendering
Display messages as text, preserving line breaks and wrapping long content. HTML-like input must not execute. Avoid raw HTML injection. Render timestamps with valid time metadata and readable formatting without hydration mismatches.

B09 — Retry integrity
Do not automatically retry an ambiguous insert with a new identity and create duplicate posts. Use the simplest appropriate protection, such as a stable client-generated submission UUID and a primary-key check/reconciliation when the response is lost, if compatible with the selected schema. Explain the actual guarantee rather than claiming universal exactly-once delivery.

B10 — Responsive and accessible interaction
The complete posting flow works with keyboard and touch at phone and desktop sizes. Feedback is readable, focus remains sensible, and the page has no overlapping controls or horizontal overflow.
